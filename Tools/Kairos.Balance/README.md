# KAIROS Balance Lab

无需 Unity、AI、联网或第三方库的数学平衡工具。Python 3.10+；本次运行环境3.13。它回答“配方抽样、时间/伤害断点、条件收益发生了什么变化”，**不生成虚假的职业胜率或总战力排行榜**。

机制总文档：[`docs/KAIROS_属性计算与平衡评估.md`](../../docs/KAIROS_属性计算与平衡评估.md)。候选尚未应用到正式卡池。研发期不做旧存档迁移；工具不会删除/读取玩家存档。

## 1. 快速复跑

从项目根目录执行（Windows Git Bash/PowerShell均可）：

```sh
python -m unittest discover -s Tools/Kairos.Balance -v
python Tools/Kairos.Balance/balance.py --out Library/Locus/tmp/balance-current
python Tools/Kairos.Balance/balance.py --patch Tools/Kairos.Balance/candidate-v02.json --out Library/Locus/tmp/balance-candidate
```

需交付可追溯报告时，把`--out`换成`docs/balance/<版本>`。输出只覆盖指定目录中的同名报告，不会修改源JSON、Unity资源、场景或存档；不要混用不同模型的旧输出文件。

入口默认为`docs/data/cards.json`；`--data`可指定完整卡池；`--model`指定另一个模型；`--patch`应用候选字段覆盖；`--decks`追加自定义配方JSON数组。不需要pip install。

## 2. 文件与每列解释

|输出|内容/用途|
|---|---|
|report.md|便于阅读的摘要，假设和限制一起输出|
|analysis.json|全部结果、模型、候选、规范化输入与工具源码SHA256；无需依赖聊天记录复现|
|cards.csv|46牌基础属性/费用/最早基础视界时点、文字；最早时点不含减费且不是最早实际抽到|
|schools.csv|六学派（含中立）的卡池功能覆盖；不是职业排名|
|decks.csv|份数加权的侍从、主动部署、早期部署、守卫、成长、响应专用数量|
|draws.csv|不放回抽样的期望、零/一/二张概率；两段精确调度仅对初始5/6张填值|
|deployment.csv|起点0…11普通部署支付后是否跨钟/就绪/成长；未来攻击时点是机会，不是必然拥有行动权|
|duels.csv|按份数加权的双方侍从配对；0/1/3/5钟，防守有/无盾，单次击杀/存活、+1攻击/HP断点|
|removal.csv|己方预组侍从对1…6伤包的脆弱性，含奥瑞斯固定入场生命和存活后的成长|
|growth.csv|存活者体型与假设每钟存活率0.5/0.75/1.0的活体期望；不把死者算成长|
|keepers.csv|10钟主费用、冷却、条件和完整技能；含0/16刻窗口冷却机会理论上界、可用率扫描|
|keeper_scenarios.csv|10钟主原生单位的情景收益：刻、生命、卡、攻击机会、信息等分别输出；source保留对应效果|
|effects.csv|全部85个显式/自动节点、IF分支路径、触发与限次、原参数；复杂效果保持符号化不硬评分|
|probability.csv|固定预见1、固定2、50%额外1的期望/方差/目标发现概率|
|time.csv|起点0…15、领先差0…8、可付费用；行动权、契机、新鸣钟、减1的非线性变化|
|candidate-data.json|只在使用patch时生成；完整候选便于引擎校验，**不是自动安装文件**|

CSV为UTF-8 BOM，Excel可直接打开筛选。布尔列True/False；空白是“不适用”，不是0。

## 3. 改模型/加牌组

### 模型输入

复制`model.json`再调整（保留基准）：

- `rules`：本工具采用的普通构筑/时轴配置；与正式引擎默认值保持一致。工具不会修改`RulesConfig`。它是分析子集，不是所有游戏设置。
- `draw_samples`：抽样张数，非时标。建议保留5/6以显示摘要，再加8/10/12。
- `growth_chimes`：已存活鸣钟数，不是双方共同轮数。
- `survival_per_chime`：独立存活的压力假设，不能伪装成实测。
- `condition_probabilities`：目标/窗口可用率扫描；不等于契机/连拍的真实概率。
- `keeper_window_end`：含起点与终点的己方时标窗口；冷却机会仅为上界。
- `probability_study`：基础可看张数、额外张数、概率、剩余池/目标数；抽牌、看牌、保留手牌不能混淆。

部分情景明确写死“25剩余/8目标、3费下一牌、3伤包”，用于统一对照；见`keeper_scenarios.csv/scenario`。改变这些情景应一起更改代码和测试，不把它们误称通用估值公式。

### 加牌组

`--decks`输入是JSON数组，结构与源卡池`precons`一致：

```json
[
  {
    "key": "MY_DECK_V1",
    "name": "我的30张诊断构筑",
    "keeper": "K_DAWN_AXUN",
    "cards": { "DAWN_SCOUT": 2 }
  }
]
```

以上只是结构示例，**故意未满30张，会被拒绝**。实际可复制源卡池某套完整`cards`再改；保留同名上限、最多两非中立学派并包含钟主学派。要比较同学派双钟主，复制同一30张配方、换独立key与keeper，再追加；不要同时改变牌表后把差异全归因于钟主。

```sh
python Tools/Kairos.Balance/balance.py --decks Library/Locus/tmp/my-decks.json --out Library/Locus/tmp/roster-analysis
```

工具会为所有配方做两两侍从截面。没有AI，不会挑选出牌，不存在“工具偷看手牌”的优势。

### 改卡/技能候选

`candidate-v02.json`使用目标kind+key、`set`顶层字段覆盖；数组/对象是**整项替换而非递归合并**。例如改ability必须填写完整name/cost/cooldownBars/targets/effects。`base_version`必须匹配源；重复目标、改key、未知字段会拒绝。

每项写reason：预期改善哪条计算路径、变差什么、可用哪张表验证。建议把当前组合包拆成单项patch做消融：仅配方/仅基础体型/仅技能，再合并。不能用相同0.2候选名代表后来不同参数；至少保留hash与版本。

未知op/关键字段/关键字/目标选择器直接报错；支持的复杂效果也不是全部自动算价，而是输出原逻辑与人工情景。有新触发或随机分支时，先补模型/单测再做评估。

## 4. 如何审阅一次报告

按顺序检查，而不是先看总分：

1. **输入相同吗？** 检查source/model/patch hash；正式数据和Unity副本仍应一致。
2. **合法且功能完整吗？** 30张、早期主动场面、回答守卫/护盾/成长的方法、合理终结手段。
3. **稳定性是多少？** 比较起手无早期单位、抽10张期望场面、调度效果；快攻需要稳定性，不应靠偶尔神抽补偿系统性弱势。
4. **强弱发生在哪里？** 筛`duels.csv`中0钟和3钟；看2/3/4伤阈值、增1攻击/生命是否改变结论。只比较相近时值或部署窗口，不把7费与1费混为等价。
5. **时间是否算错？** 检查支付后鸣钟、临时buff过期、减费导致失去契机、被推者得到成长、攻击仍付节奏。
6. **条件收益是否能兑现？** 每个技能同时列下界/上界，p低/中/高；未满足条件的能力不是有印刷文字就满额得分。
7. **需要引擎复核哪些情景？** 抢拍、亡语、推迟、逆流、同时死亡、满手焚毁、场地变化等不能靠单次交换表证明。
8. **记录结论和反例**：哪条结构差异已改善，哪名钟主缺测，是否真的新增玩家选择；不宣称达到某个目标胜率。

本工具没有自动发布/自动调参/自动替换正式卡池；这样不会把一次数学候选误当平衡验收通过。用户已授权研发调整，但当前任务按最新要求优先交付可复用依据和工具。

## 5. Machinations 可选推演蓝图

无需Machinations账号即可运行上述工具。本节提供**手工搭建说明，不是已导入/执行过的Machinations工程，也未验证其当前UI控件名称**。不要把仅有资源流的近似图当正式规则引擎。

### 5.1 最小资源流图

为双方各建一组，以A为例：

|节点|初值/类型概念|连接与作用|
|---|---|---|
|DeckA|30张有身份的牌；若只能放数量token则是近似|SetupDraw→HandA；Draw每次移1；不得有放回|
|HandA|先5/后6、容量8|PlayGate扣1；Draw溢出→PastA；不能自动保证打出抽到的牌|
|LifeA|20，上限20|伤害/支付扣；治疗夹上限；0→终局|
|MarkerA|0…64，整数状态|付款/推迟增加；逆流有限后退；ActionGate按双方位置开放|
|ChimesRungA|最高已鸣钟序号|当逐刻抵达4…60且序号更高才触发ChimeA|
|HorizonA|`min(7,2+ChimesRungA)`|限制普通动作，不限制Wait|
|BoardA|最多5实体槽，每槽记录Atk/Hp/Cadence/Ready/Stasis/Shield/Growth|部署从Hand进入；死亡→Past；不能只用一个“战力token”代替所有单位|
|SandA|0…10|死触发/牺牲加；仅打牌减费消耗；下限费用1|
|AbilityReadyAtA|0|宣言时设Rung+CD；不是每现实秒衰减|
|Omen/ChannelA|带Owner/位置/目标的实体队列|逐刻事件顺序处理；不能同时与鸣钟并行|
|ActionQueue|一个原行动＋最多一次响应|锁费用→响应结算→原行动→付款；顶层选择可暂停|

如果平台token不能携带牌身份/无放回洗牌，可用每卡一个池＋剩余数量加权抽取并抽后扣除；若也难表达，**抽样模块直接用本工具的精确结果**，不要用每次固定K/N独立抽取冒充牌库。

### 5.2 事件驱动次序

一次仿真步必须表示“原子规则事件”，不能固定表示“一方一个回合”。依次：

1. `PendingChoice/Response`优先，否则较小时标可行动，同刻较大LastMoveSeq可行动。
2. 从外部固定动作脚本或明确策略选择动作，计算最终费用/合法目标，不允许先扣资源再发现非法。
3. 锁定契机/连拍，扣砂/手牌，设置疲惫/CD；打开一次响应。
4. 完整结算响应，再结算原动作效果；伤害同时快照反击；状态检查和死亡FIFO。
5. 每前进1刻：伏笔→本方咏唱/回声→新鸣钟。鸣钟：抽1；解除停滞或重整；清临时buff/限次；触发成长等；暮钟损命。
6. 预言补抽→命烛检查→逆流→64比较，再开放下一动作。

Machinations难以严格实现步骤4/5时，把它用于**资源预算与敏感性图**即可；精确战斗/顺序必须由C#引擎复核。不要用同一时步同时刷新双方。

### 5.3 建三张小图，比一张全游戏大图更可靠

**图A：起手供应**
- 输入N=30，K=8或10，先5/后6；做不放回抽样；输出无早期部署次数、至少2张次数。
- 换掉非目标时先放回牌库再抽，保留目标不放回。
- 校准：大量重复近似18.48%/10.88%，不要为了贴合结果修改RNG；精确值以Python公式为准。

**图B：成长/回答窗口**
- 三种单位：1/3蓄力、2/1迅捷、1/5守卫；输入部署起点、下一解牌伤害2/3/4、攻击节奏。
- 跑0/1/3/5个自己鸣钟，按存活率s=.5/.75/1.0扫描；记录存活者体型与总体活体期望，不混用分母。
- 输出被3伤击杀的时点、额外攻击次数、累计支付，而非“成长职业胜率”。

**图C：技能与局部随机**
- 先单独比较阿迅：付1→下张3费减1或减2；设置25/50/75%兑现率，跨钟则状态移除；输出净省刻。
- 再比较额外预见：固定1＋概率p额外1，p从0到1，每档.1；输出均值/方差/目标发现率。
- 支持种子时固定并记录；若不支持，就注明无法逐次重现，只比较统计量。

### 5.4 实验记录与统计误差

每次记录：模型版本、输入卡池hash、所采用规则近似、种子或不可复现说明、重复数N、事件/样本数、均值、标准差、置信区间、失败/超步数。概率采样标准误近似`sqrt(p(1-p)/N)`，N=10000、p=.5时95%区间半宽约0.98个百分点；只有独立重复试验才适用。复杂同种子配对差异应用配对样本方法，不把一场内多次攻击算独立对局。

有确定性公式时用精确公式；仿真是检查过程和近似模型，不是靠“跑很多次”消除错误规则。

### 5.5 必须通过的交叉校准用例

- 先手5张/后手6张、同种子可复现；精确无早期侍从概率与Python一致。
- 3刻付2→鸣钟4一次并到5；7刻回退但最高已鸣8，重过8不再鸣；64不鸣。
- 3/2对2/3无盾同死；防守有盾则防守存活、进攻仍死；0伤不破盾。
- 1/3蓄力付2从2到4→本次付款即2/4且就绪；不是等对手走完一回合。
- 停滞第一钟解状态但不就绪，第二钟才就绪；期间成长照常。
- 阿迅在3刻用1刻技能→4刻清临时减费；收益不是固定净赚。
- 任何无法准确实现的项写入报告限制，不纳入数值调优结论。

## 6. 自动验证与可维护性

```sh
python -m unittest discover -s Tools/Kairos.Balance -v
dotnet test Tools/Kairos.Tests --no-restore
```

Python测试用小牌库全组合穷举校准超几何/两段调度，而不是用同一公式自证；同时覆盖盾/同时伤害/旧钟与64、成长条件化、完整卡池/候选、错误数据拒绝、确定性再生成、禁止向Assets输出。

C#既有测试保证当前可玩引擎行为，但本轮候选尚未实装，因此现有78项通过**不等于候选技能/概率机制已通过引擎回归**。
